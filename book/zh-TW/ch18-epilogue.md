# 第十八章：我們學到了什麼

## 五個架構賭注

Claude Code 不是唯一的 agentic 系統。也不是第一個。但它做出了五個架構賭注，使其有別於 agent 框架的整體版圖，而經過近兩千個檔案和十七個章節之後，這些賭注值得深入審視。

### 賭注一：Generator 迴圈勝過 Callback

大多數 agent 框架給你一個 pipeline：定義工具、註冊 handler、讓框架來編排。開發者撰寫 callback。框架決定何時呼叫它們。

Claude Code 做了相反的事。`query()` 函式是一個 async generator——開發者掌控迴圈。模型串流回應，generator yield tool call，呼叫端執行它們、附加結果，然後 generator 繼續迴圈。只有一個函式、一條資料流、一個所有互動都必須通過的地方。Generator 回傳型別中的 10 個終止狀態和 7 個延續狀態，編碼了每一種可能的結果。迴圈就是系統本身。

這個賭注是：一個單一的 generator 函式，即使膨脹到 1,700 行，也比分散的 callback 圖更容易理解。研究原始碼之後，這個賭注得到了回報。當你想理解一個 session 為何結束時，你看一個函式。當你想新增一個終止狀態時，你在一個判別聯合型別中加一個變體。型別系統強制窮舉處理。Callback 架構會把這些邏輯分散到數十個檔案中，而 callback 之間的互動會是隱式的，而非在控制流中可見。

### 賭注二：檔案式記憶體勝過資料庫

第十一章已經詳細論述了這一點，但其架構意義不僅限於記憶體。選擇使用純 Markdown 檔案而非 SQLite、向量資料庫或雲端服務，是一個「透明度勝過功能性」的賭注。資料庫能支援更豐富的查詢、更快的查找和交易保證。檔案什麼都不提供。檔案提供的是信任。

一個使用者打開 `~/.claude/projects/myapp/memory/MEMORY.md`，在 vim 中看到 agent 記住的每一件事——這位使用者與系統的關係，和那些必須問 agent「你記得什麼？」然後祈禱答案完整的使用者，是根本不同的。檔案式設計讓 agent 的知識狀態可以從外部觀察，而不僅僅是自我報告。這比查詢效能重要得多。LLM 驅動的召回系統用檢索智慧來補償儲存的簡單性——一個 Sonnet 側查詢從清單中選出五筆相關記憶，比 embedding 相似度更精確，而且不需要任何基礎設施。

### 賭注三：自描述工具勝過中央編排器

Agent 框架通常提供一個工具註冊表：你在中央配置中描述工具，框架將它們呈現給模型。Claude Code 的工具描述自己。每個 `Tool` 物件攜帶自己的名稱、描述、輸入 schema、prompt 貢獻、並行安全旗標和執行邏輯。工具系統的工作不是向模型描述工具——而是讓工具描述自己。

這個賭注在可擴展性上得到了回報。MCP 工具（第十五章）透過實作相同的介面成為一等公民。來自 MCP server 的工具和內建工具，對模型而言是無法區分的。系統不需要單獨的「MCP 工具適配層」——包裝產生一個標準的 `Tool` 物件，從那一刻起，現有的工具管線處理它：權限檢查、並行執行、結果預算、hook 攔截。

### 賭注四：Fork Agent 實現快取共享

第九章涵蓋了 fork 機制：一個子代理，以父代的完整對話作為其上下文視窗的起點，共享父代的提示詞快取。這不是一個便利性最佳化——這是一個架構賭注，認為快取共享模型值得 fork 生命週期管理的複雜性。

替代方案——用對話摘要產生一個全新的 agent——更簡單但更昂貴。每個全新的 agent 都要支付從頭處理其上下文的全部成本。Fork 出來的 agent 免費獲得父代的快取前綴（輸入 token 享有 90% 折扣），使得為小任務產生 agent 變得經濟實惠：記憶體萃取、程式碼審查、驗證流程。背景記憶體萃取 agent（第十一章）在每次 query loop 回合後執行，其成本微乎其微，正是因為它共享了父代的快取。沒有基於 fork 的快取共享，那個 agent 的成本會高到令人望而卻步。

### 賭注五：Hooks 勝過外掛

大多數可擴展性系統使用外掛——註冊功能並在宿主行程中執行的程式碼。Claude Code 使用 hooks——在生命週期節點執行的外部行程，透過 exit code 和 stdin/stdout 上的 JSON 進行通訊。

這個賭注是：行程隔離值得其開銷。外掛可能讓宿主崩潰。Hook 只會讓自己的行程崩潰。外掛可能把記憶體洩漏到宿主的 heap 中。Hook 的記憶體隨行程消亡。外掛需要一個必須版本管理和維護的 API 表面。Hook 只需要 stdin、stdout 和 exit code——一個自 1971 年以來就穩定的協定。

開銷是真實的：每次 hook 調用產生一個行程，消耗的毫秒數是行程內 callback 不會有的。第十二章中內部 callback 的 -70% 快速路徑表明，系統知道這個成本很重要。但對於外部 hooks——使用者腳本、團隊 linter、企業策略伺服器——隔離保證讓系統更安全地被擴展。企業可以部署基於 hook 的策略執行，而不必擔心格式錯誤的 hook 腳本會讓開發者的 session 崩潰。

## 哪些可遷移，哪些不行

並非 Claude Code 中的每個模式都能通用化。有些是規模、資源或特定約束的結果，而其他 agent 開發者可能不會面對相同的條件。

### 可遷移到任何 Agent 的模式

**Generator 迴圈模式。** 任何需要串流回應、處理 tool call 和管理多個終止狀態的 agent，都能從讓迴圈顯式化——而非隱藏在 callback 背後——中獲益。判別聯合型別的回傳型別——精確編碼迴圈停止的原因——是一個能消除整類「agent 為什麼停了？」除錯 session 的模式。

**檔案式記憶體搭配 LLM 召回。** 具體的實作細節屬於 Claude Code，但原則——簡單儲存搭配智慧檢索——適用於任何需要跨 session 持久化知識的 agent。四類分類法（使用者、回饋、專案、參考）和可推導性測試（「這能從當前專案狀態重新推導嗎？」）是可重用的設計啟發法則。

**非對稱讀寫通道用於遠端執行。** 當讀取是高頻串流、寫入是低頻 RPC 時，將它們分開是正確的，無論使用什麼具體傳輸協定。

**Bitmap 預篩選用於搜尋。** 任何在大型檔案索引中搜尋的 agent 都能從 26 位元字母 bitmap 作為預篩選中獲益。每個條目四個位元組，每個候選項一次整數比較——成本效益比非常出色。

**提示詞快取穩定性作為架構關注點。** 如果你的 agent 使用具有提示詞快取的 API，將穩定內容放在前面、易變內容放在後面來結構化 prompt，這不是最佳化——這是一個決定你成本結構的架構決策。

### 特定於 Claude Code 規模的模式

**Fork 出來的終端機渲染器。** Claude Code fork 了 Ink 並用 packed typed array、基於 pool 的 interning 和 cell 級別 diff 重新實作了渲染管線，因為它需要在終端機中達到 60fps 串流。大多數 agent 渲染到 web 介面或簡單的 log 輸出。只有當終端機渲染是你的主要 UI 且你在高頻串流時，這個工程投資才有意義。

**50 多個啟動分析檢查點。** 當你有數十萬使用者且 0.5% 的取樣能產生統計顯著數據時才有意義。對於較小的 agent，更簡單的計時系統就足夠了。

**八種 MCP 傳輸類型。** Claude Code 支援 stdio、SSE、HTTP、WebSocket、SDK、兩種 IDE 變體和一個 Claude.ai proxy，因為它必須與每種部署拓撲整合。大多數 agent 只需要 stdio 和 HTTP。

**Hooks 快照安全模型。** 在啟動時凍結 hook 配置，之後絕不隱式重新讀取，是對一種特定威脅的防禦：惡意儲存庫程式碼在使用者接受信任對話框之後修改 hooks。當你的 agent 在帶有不受信任 `.claude/` 配置的任意儲存庫中執行時，這很重要。只在受信任環境中執行的 agent 可以使用更簡單的 hook 管理。

## 複雜性的代價

近兩千個檔案。這買到了什麼，又付出了什麼代價？

檔案數量作為複雜性指標是有誤導性的。其中大部分是測試基礎設施、型別定義、配置 schema 和 fork 出來的 Ink 渲染器。實際的行為複雜性集中在少數高密度檔案中：`query.ts`（1,700 行，agent 迴圈）、`hooks.ts`（4,900 行，生命週期攔截系統）、`REPL.tsx`（5,000 行，互動式編排器），以及記憶體系統的 prompt 建構函式。

複雜性來自三個來源，各有不同的特質：

**協定多樣性。** 支援五種終端機鍵盤協定、八種 MCP 傳輸類型、四種遠端執行拓撲和七個配置範圍，本質上就是複雜的。每增加一個協定是對程式碼庫的線性增加，而非指數增加——但總和很大。這種複雜性在 Brooks 意義上是偶然的：它來自環境（終端機碎片化、MCP 傳輸演進、遠端部署拓撲），而非來自正在解決的問題本身。

**效能最佳化。** 基於 pool 的渲染、bitmap 搜尋預篩選、sticky 快取鎖存和推測性工具執行，每一項都以複雜性換取可測量的效能提升。這種複雜性被測量所證明——每項最佳化之前都有效能分析數據識別出瓶頸。風險在於最佳化會累積並以使熱路徑更難修改的方式相互作用。

**行為調校。** 記憶體系統的 prompt 指令、過期警告、驗證協定、「忽略記憶體」反模式指令——這些不是程式碼複雜性。它們是 prompt 複雜性，帶有不同的維護負擔。當模型行為在版本之間發生變化時，透過 eval 仔細調校的 prompt 指令可能需要重新調校。Eval 基礎設施（在整個程式碼庫中以案例編號和 eval 分數的形式出現）是防止回歸的防線，但它需要持續投入。

這個系統的維護負擔是顯著的。一個新工程師閱讀程式碼庫時，不僅要理解程式碼路徑，還要理解促成特定 prompt 措辭的 eval 結果、促成特定安全檢查的生產事故，以及促成特定最佳化的效能分析。程式碼註解很詳盡——許多包含 eval 案例編號和前後對比測量——但近兩千個檔案中的詳盡註解本身就是閱讀負擔。

## Agentic 系統的發展方向

從 Claude Code 的模式中可以看到四個趨勢，它們指向這個領域的未來走向。

### MCP 作為通用協定

第十五章描述了 Claude Code 是最完整的 MCP 客戶端之一。重要的不是 Claude Code 的實作——而是 MCP 的存在本身。一個標準化的工具發現和調用協定意味著，為一個 agent 建構的工具可以與任何 agent 一起使用。生態系統效應是顯而易見的：一個 Postgres 的 MCP server 一旦建成，就能服務每一個使用 MCP 的 agent。開發者在工具整合上的投資是可攜帶的。

對 agent 開發者的啟示：如果你正在定義自訂工具協定，你很可能犯了一個錯誤。MCP 已經夠好了，它正在變得更好，而標準協定的生態系統優勢會隨時間複合累積。建構一個 MCP 客戶端、貢獻 spec，讓協定透過社群回饋來演進。

### 多 Agent 協調

Claude Code 的子代理系統（第八章）、任務協調（第十章）和 fork 機制（第九章）是多 agent 模式的早期實作。它們解決特定問題——快取共享、平行探索、結構化驗證——但它們也揭示了根本挑戰：協調開銷。

Agent 之間的每一條訊息都消耗 token。每個 fork 共享快取但增加了一個對話分支，父代最終必須調和。Task 系統的狀態機（queued、running、completed、failed、cancelled）是增加複雜性但不增加能力的協調機制。隨著 agent 變得更有能力，壓力將從「我們如何協調多個 agent？」轉向「我們如何讓一個 agent 足夠有能力，使協調變得不必要？」

目前的證據表明兩種方法將共存。簡單任務使用單一 agent。複雜任務使用協調的多 agent 系統。工程挑戰在於讓協調開銷低到足以使交叉點偏向多 agent 用於真正的平行工作，而不僅僅是用於複雜的任務。

### 持久化記憶體

Claude Code 的記憶體系統是持久化 agent 記憶體的第一版。檔案式設計、四類分類法、LLM 驅動的召回、過期系統，以及用於長時間 session 的 KAIROS 模式，都是一個將大幅演進的問題的第一代解決方案。

未來的記憶體系統很可能會加入結構化檢索（當前系統檢索整個檔案；未來系統可能檢索特定事實）、跨專案遷移學習（適用於所有地方的使用者偏好、不適用的專案慣例），以及協作記憶體（第十一章的團隊記憶體是第一步，但同步、衝突解決和存取控制都是最小化的）。

開放的問題是：檔案式方法是否能規模化。在每個專案 200 條記憶時，它能運作。在每個專案 2,000 條記憶時，Sonnet 側查詢的清單會變得太大，合併會變得太昂貴，索引會超出其上限。檔案勝過資料庫的架構賭注，將在使用量增長時面臨最嚴峻的考驗。

### 自主運作

KAIROS 模式、背景記憶體萃取 agent、自動 dream 合併、推測性工具執行——這些都是邁向自主運作的步驟。Agent 在沒有被要求的情況下做有用的工作：它記住你忘了告訴它要記住的東西，它在你睡覺時合併自己的知識，它在當前回應完成之前就開始執行下一個工具。

軌跡很清楚。未來的 agent 將更少是被動的、更多是主動的。它們會注意到使用者未描述的模式，建議使用者未請求的修正，並在沒有明確 `/remember` 指令的情況下維護自己的知識。Claude Code 的記憶體系統，憑藉其背景萃取安全網和經過 prompt 工程的「要保存什麼」啟發法則，就是這個未來的原型。

約束是信任。自主運作要求使用者信任 agent 在無人看管時會做正確的事。檔案式記憶體、可觀察的 hook 系統、過期警告、權限對話框——所有這些之所以存在，是因為信任必須被贏得，而非被假設。通往更自主 agent 的路，經過更透明的 agent。

## 結語

十七個章節。六個核心抽象層。一個 generator 迴圈居於中心，工具向外延伸，記憶體穿越時間向後延伸，hooks 守衛邊界，一個渲染引擎將這一切轉譯成螢幕上的字元，而 MCP 將它連接到程式碼庫之外的世界。

Claude Code 中最深層的模式不是任何單一技術。它是一個反覆出現的決策：將複雜性推向邊界。渲染系統將複雜性推向 pool 和 diff——在管線內部，一切都是整數比較。輸入系統將複雜性推向 tokenizer 和 keybinding resolver——在 handler 內部，一切都是型別化的 action。記憶體系統將複雜性推向寫入協定和召回選擇器——在對話內部，一切都是上下文。Agent 迴圈將複雜性推向終止狀態和工具系統——在迴圈內部，就只是：串流、收集、執行、附加、重複。

每一個邊界吸收混亂並輸出秩序。原始位元組變成 `ParsedKey`。Markdown 檔案變成被召回的記憶。MCP JSON-RPC 變成 `Tool` 物件。Hook exit code 變成權限決策。在每個邊界的一側，世界是混亂的——五種鍵盤協定、脆弱的 OAuth 伺服器、過期的記憶、不受信任的儲存庫 hooks。在另一側，世界是型別化的、有界的、且被窮舉處理的。

如果你正在建構一個 agentic 系統，這就是可遷移的教訓。不是具體的技術——你可能不需要基於 pool 的渲染、KAIROS 模式或八種 MCP 傳輸。但那個原則：定義你的邊界，在那裡吸收複雜性，保持邊界之間的一切乾淨。邊界是工程困難的地方。內部是工程愉快的地方。為愉快的內部而設計，把你的複雜性預算投資在邊緣。

原始碼是開放的。螃蟹的螯上握著地圖。去讀它吧。
